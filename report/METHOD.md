# 측정 기준

## 비교할 구현

| 정렬 | 구현 | 안정성 | 추가 공간의 차수 |
| --- | --- | --- | --- |
| 삽입 | 앞쪽의 큰 원소를 한 칸씩 이동 | 보장 (`>`일 때만 이동) | O(1) |
| 병합 | 반으로 분할한 뒤 보조 배열에 병합 | 보장 (같으면 왼쪽 먼저) | O(n) 보조 배열 + O(log n) 호출 스택 |
| 힙 | 바닥부터 최대 힙 구성, 최댓값 교환, 반복 siftDown | 보장하지 않음 | O(1) |

병합은 이미 정렬된 구간도 병합하는 기본 구현이며 조기 종료를 넣지 않았다.
삽입도 매 회전의 임시 저장과 재배치를 생략하지 않는다. 따라서 오름차순
입력에서도 이동이 `2(n-1)`회다. 교수님 샘플의 최적화된 삽입 구현에서
이동 0회가 나오는 것과는 구현이 다르다.

## 입력과 반복

- 크기: 1,000 / 2,000 / 4,000 / 8,000. 3개 정렬 × 4개 크기 × 4개 입력 = 48행.
- 무작위: 0부터 n-1까지의 서로 다른 정수를 섞는다.
- 오름차순과 내림차순: 같은 0부터 n-1까지의 정수다.
- 중복 많음: 0~15의 값으로 채운다.
- xorshift32의 씨앗은 `20260930+n`이다. 나머지 연산을 사용하므로 난수
  분포에 미세한 편향이 있으며, 엄밀한 균등 표본이라고 주장하지 않는다.
- 각 조건의 동일 입력을 복사해 세 알고리즘에 제공한다. 각각 5회 반복한다.
  이는 같은 입력의 시간 반복 측정이며 서로 다른 무작위 입력 5개의 평균이 아니다.

## 각 숫자의 의미

- **comparisons:** `compareKeys` 한 번을 원소의 키 비교 1회로 센다.
  인덱스 검사와 정렬 결과 확인의 비교는 제외한다. 비교 함수 내부의 C 연산자
  수나 CPU 명령 수를 세는 지표가 아니다.
- **moves:** `Record` 하나의 임시 저장 또는 배열 대입 1회를 이동 1회로 센다.
  교환은 3회다. key와 tag를 각각 세지 않으며 병합의 버퍼 저장·복귀도 센다.
  자기 위치에 다시 쓰는 삽입 정렬의 대입도 포함한다.
- **mean_ms:** `clock()`으로 잰 프로세스 CPU 시간의 5회 평균이다.
  입력 생성·복사·검사·출력은 제외한다. 정렬 내부의 계수 연산과 병합의
  메모리 할당·해제는 포함한다. 계수 없는 최적화 코드의 순수 속도와는 다르다.
  매우 짧은 구간은 타이머 해상도와 부하의 영향을 크게 받으며 0이 나올 수도 있다.
- **extra_record_bytes:** 정렬 알고리즘의 추가 `Record` 저장 공간을 계산한다.
  삽입·힙은 원소 1개, 병합은 n개다. 실제 `sizeof(Record)`를 사용하며 패딩도
  포함한다. 인덱스·포인터·호출 스택·할당기 관리 공간·측정용 배열은 제외한다.
  프로세스 전체 메모리를 실측한 값이 아니다.
- **max_recursion_depth:** 병합 정렬의 루트를 1로 두고 기본 구간 호출까지 센다.
  반복 구현인 삽입·힙은 1이다. 이 수는 전체 C 함수 호출 깊이나 스택 바이트가 아니다.
- **equal_key_order:** 이 입력에서 같은 키의 순서가 유지되면 yes, 뒤집히면 no,
  같은 키가 없으면 n/a다. yes 하나로 모든 입력에서의 안정성을 증명할 수 없다.

## 정확성과 안정성

원소는 `(key, tag)`이고 tag는 정렬 직전 원래 위치다. 세 정렬은 key만 비교한다.
오름차순 여부와 함께 모든 tag가 한 번씩 등장하고 원래 key와 짝을 유지하는지
검사한다. 정렬 후 같은 key끼리 tag가 오름차순인지 검사해 안정성을 확인한다.
이 검증에 쓰는 공간과 시간은 측정 구간 밖에 있다.

`make demo`의 입력은 `(2,0) (1,1) (2,2)`다. 힙 정렬의 결과에서는
`(2,2)`가 `(2,0)`보다 앞에 놓인다. 정렬 자체는 맞지만 안정적이지 않은 사례다.
삽입과 병합의 안정성은 각각 같은 키를 넘겨 이동하지 않는 규칙과 왼쪽 우선
병합 규칙으로 설명하고, 테스트는 구현 실수를 검출하는 용도로 사용한다.

테스트는 -1/0/1로 이루어진 길이 0~7의 모든 배열, 극단 정수값, 여러 길이와
입력 형태를 확인한다. 기준 결과는 C 표준 `qsort`에서 key 다음 tag 순으로
만든다. 이것은 테스트의 정답 생성에만 사용하며 실제 정렬은 tag를 비교하지 않는다.
원소 소실·중복·잘못된 tag를 검출하는 검사 자체도 별도로 시험한다.

## 재현과 한계

```sh
make test
make results
```

`results.csv`, `environment.json`, `stability_demo.txt`가 새로 만들어진다.
코드·씨앗·원소 크기가 같으면 비교·이동 횟수는 재현된다. 실행 시간은 장비,
컴파일러, 부하에 따라 달라진다. 공유 실행 환경에서는 다른 환경의 숫자와
절대 속도를 비교하지 않는다. 한 가지 씨앗과 제한된 n 범위의 결과를 모든
입력에 일반화하지 않는다. 컨테이너 설정이 있다는 것과 실제 그 컨테이너에서
실험했다는 것은 다르므로, 보고서 환경은 반드시 environment.json을 따른다.
